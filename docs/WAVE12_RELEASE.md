# Wave 12 — Runtime guardrails

Content/build **0.13.0**, save schema **5**. This wave extends the existing Frontier Lab game with an optional product operating layer. The interface remains a sparse page of ordinary buttons, compact metrics, short tables and expandable sections.

## What is playable

The new loop is **exact model reports → paid checker rollout and paired audit → recurring inference work → customer feedback and capacity decisions → configuration-bound release evidence**.

Wave 11 taught models a limited policy boundary. Wave 12 lets a company operate an additional response checker for **Basic Chat and Developer API**. The player chooses a balanced or strict profile, pays implementation work, inspects the same finite before/after audit, and then pays the checker’s real serving workload. The profile can be disabled without discarding its completed work or evidence.

All profile rates, policy cases, costs and outcomes are authored game rules. A successful finite audit is not a guarantee about every future request. Ordinary public traffic remains an authored allowed-request workload; restricted requests appear in the separate audit. The game does not silently create a population of harmful customers or treat justified policy refusals as customer-service failures.

## Unlocks, rollout and recurring costs

**Behavior cases (R1A)** and **Preference tuning (R5)** unlock the controls under each Chat/API product’s **Runtime guardrails** section. The product must already be deployed. Its primary model and any enabled routing secondary each need their own exact, completed, paid capability and policy-boundary reports. A copied report, a report from another model version, or an unpaid scenario report does not qualify.

The existing model commercial-admission check remains in force. A policy-trained model that failed its own required policy report cannot use runtime checking to bypass that gate. Hosted-use rights, product eligibility, connected memory and compatible hardware still apply.

| Property | Balanced | Strict |
|---|---:|---:|
| Development rollout, including the paired audit | 2 CUw | 2 CUw |
| ML implementation and review | 2 staff-weeks | 2 staff-weeks |
| Maximum progress per calendar week | 1 CUw and 1 staff-week | 1 CUw and 1 staff-week |
| Extra serving work per request | 0.00002 CUw | 0.00005 CUw |
| Extra serving work per 1,000 requests | 0.02 CUw | 0.05 CUw |
| Additional resident checker memory | 1 MU | 2 MU |
| Interception of otherwise unsafe restricted compliance | 70% | 90% |
| Fraction of otherwise useful allowed answers withheld | 2% | 8% |

There is no separate upfront purchase fee. Existing payroll, reserved cloud capacity and owned-hardware operating rules pay for actual implementation grants. GPU progress and ML progress can finish independently; neither substitutes for the other. A stalled rollout retains completed work. Both meters must finish before the report and operating profile become available at the **following weekly boundary**.

The rollout needs one compatible connected pool with the captured primary model, any routed model, one session workspace, and the checker’s additional memory. Sparse models retain their fabric requirements. After activation, ordinary product demand reserves the checker memory alongside model weights and customer sessions. The checker is not a free capability unlocked by completing research.

A replacement is staged: the currently enabled checker continues on matching inputs while the new profile is built. When the replacement activates, it supersedes the earlier installation. Only the latest completed installation can be enabled. Returning to an earlier profile is allowed through another paid rollout; identical inputs and profiles produce the same audit again. The retained history is bounded at **eight installations per product and sixteen overall**.

### Cost and billing semantics

Checker work is added **after routing and prefix-cache discounts**. Smaller serving models and reused input prefixes can reduce ordinary inference work; they do not erase the additional checker work. Every completed checked request consumes its corresponding GPU work. A partially executed request can consume a fraction of checking work without claiming a completed check or a completed false-refusal outcome.

The added work is part of the existing product serving request and grant. It appears within physical serving work and ordinary GPU costs, with no second serving invoice or duplicate ledger expense. Physical work follows the granted hardware’s efficiency. Using already reserved cloud capacity can consume spare headroom without creating a new per-request rent charge; buying more cloud reservation changes the normal recurring cloud bill.

Checking produces **no extra billable input, output or internal customer tokens**. At equal completed request volume, enabling the checker leaves the product’s token bill unchanged. When capacity is insufficient, the larger workload can reduce fulfilled requests. Developer API revenue then follows the actual executed tokens; subscription products apply their existing service-credit rules. Billing rates, customer contracts and fractional token-bill carries are preserved.

## Paired policy audit

Each paid rollout includes a report on the same **100 reserved cases**:

- **50 allowed cases:** useful answers, confident errors, false refusals and clarifications remain separate.
- **50 restricted cases:** correct policy refusals and unsafe compliances remain separate.
- Both eligibility classes contain **25 direct and 25 adversarial cases**.

Every case records its model route and its outcome before and after the checker. The checker can turn an otherwise unsafe restricted compliance into a correct refusal. On allowed cases, it can turn an otherwise useful answer into a false refusal. It does not improve the model’s technical capability, repair a confidently wrong answer, reverse a learned refusal, or turn a clarification into a useful answer.

The audit cohort is fixed by company, seed and protocol. Profile choice, waiting, model names, model IDs, command IDs and simulation-random draws cannot reroll it. Balanced and strict profiles use the same cases and checking draws, so strict checking retains the intended tradeoff instead of drawing an easier test.

With request routing, the audit assigns **40 cases to the primary model and 60 to the secondary**, balanced within allowed/restricted and direct/adversarial groups. Each case uses that model’s own policy behavior. The secondary does not inherit the primary’s safety properties through a mixed display object. Both routes’ paid model reports and fingerprints are captured independently.

The UI also shows standard service-work estimates for the 100 probes under the captured model and feature settings. These estimates include routing overhead and precede prefix-cache savings. They explain recurring operating differences; they are not another development bill. The fixed 2-CUw rollout already includes implementation and the audit.

## Model, release and feedback connections

### Learned behavior stays separate

Runtime checking does not alter model capabilities, reliability, learned policy, confident-error behavior, planner behavior, rights or training lineage. It does not create a dataset or improve a model by collecting a report. Its recurring behavior is conditional on an enabled, available installation matching the current product inputs.

The additional allowed false-refusal rate is the selected profile’s blocked share of the model’s remaining useful answers. It is not a flat addition of two or eight percentage points to every request. For example, the earned campaign’s baseline technical-error rate is 16.71% and learned false-refusal rate is 3.85%, leaving 79.44% otherwise useful allowed responses. Integer game arithmetic adds **1.58 percentage points** with balanced checking or **6.35 points** with strict checking. The live false-refusal meter therefore becomes **5.43%** or **10.20%** while that checker runs.

The resulting false refusals feed the existing customer-friction and retention rules. There is no new automatic trust reward for turning on a profile and no general alignment score.

### Exact configuration evidence

An installation freezes the primary model, its exact report pair, any actual routing secondary and its reports, and the product’s conversation options. Changing those inputs makes the installation stale. A stale checker retains its paid report but adds no serving effect or resident checker memory. New inputs need their own paid rollout; restoring the exact already captured inputs can match their retained evidence again.

Guardrail configuration also participates in the product’s release fingerprint. The captured record includes the selected installation, profile, enabled state, input fingerprint and any pending replacement. Starting a rollout or changing its operating state can make a previous release comparison inapplicable. Prepared handovers and rollbacks freeze these choices until the preparation is completed or discarded. Unfinished checker installations prevent freezing a new prepared-release configuration.

Existing release rehearsals remain **benign model comparisons**. Their work and results do not become runtime-guardrail audits. Binding the current guardrail settings prevents stale release evidence from being reused as though the product configuration were unchanged; it does not add a policy certification to the rehearsal.

### Feedback preserves actual operating context

Prospective consented feedback still samples only actual paid allowed responses. New feedback receipts optionally record the applied checker ID, profile, input fingerprint, whether checking occurred, and the baseline and added false-refusal rates. A study can therefore retain the actual balanced and strict contexts in its separate weekly rows.

Correct restricted refusals from the audit do not become generic negative customer feedback. Audit probes are not customer usage, are not billable traffic, and do not produce reusable policy labels. The existing separate paid review, licensing, curation and training steps remain necessary before customer feedback can improve a future model. Previously collected studies and their settlement proofs remain unchanged.

It does not advance time, buy guardrails, alter models, add projects, consume cases or change the economy. Optional installation, usage, feedback and release fields remain absent until the feature is adopted.

### Lossless formatting fallback within the same limit

The full eight-installation history exposed a save-formatting issue: pretty JSON could exceed the existing two-megabyte limit while the exact same validated game state fit comfortably without formatting whitespace.

Serialization now follows a deterministic two-step rule:

1. Preserve the existing pretty-printed JSON **byte-for-byte** when it fits.
2. Only if that representation exceeds **2,000,000 UTF-8 bytes**, serialize the same envelope and complete state as compact JSON.

The hard limit remains **2,000,000 bytes** for both saves and imports. Compaction removes only insignificant JSON whitespace. It does not prune audit cases, shorten histories, change checksums, rewrite game state, or enlarge the accepted import limit. If the compact representation also exceeds the bound, saving reports the limit and preserves the last usable primary save.
