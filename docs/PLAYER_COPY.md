# Frontier Lab player wording

Write like a game explaining a choice. Start with what the player can do, what they get, what it costs and what happens next. Put technical detail behind those answers.

## Shared wording

| Use | Instead of |
| --- | --- |
| Review your choice | Review commitment |
| Cost and requirements | Current commitment |
| Confirm for Week … | Queue for Week … |
| Weekly pay | Recurring salary |
| Next week / the following week | Weekly boundary |
| Ready to use | Usable availability |
| Close and keep draft | Close / keep draft |
| Download save / Load save | Export snapshot / Import snapshot |
| Current model / new model | Incumbent / candidate, when identity is already clear |
| Live test (canary) | Metered canary, without an explanation |

Use short action labels and complete, direct explanations. Prefer “Your choices will be here when you return” to descriptions of retained task state. Explain blocked actions with the missing requirement and how to meet it. Avoid forced excitement, slogans and internal terms such as canonical, authoritative or exact identity.

## Keep the game accurate

Preserve numbers, units, restrictions, deadlines and selected model identities. Lower compute work does not necessarily mean lower cash costs. Training and testing are different actions. A queued choice is not completed work. Customer payments are income, not player expenses. Licensing must retain the most restrictive applicable permissions.

Keep useful research names and AI concepts. Explain unfamiliar units in the guide: CU is compute capacity, CUw is compute work, MU is memory, FTE is a full-time share and a staff-week is one person's full-time work for a week. Avoid replacing precise mechanics with a promise the game cannot keep.

Check labels, help text, reviews, blocked states and results together. Tests that match visible text should follow the new wording while keeping their behavioral and numeric checks.
